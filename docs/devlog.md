## 2026-09-29 — AI 호출 오류 처리 개선과 버튼 배치 (`f823d91`)

### 증상과 원인
- 실제 키를 넣은 뒤, 테스트 스크립트는 성공했는데 앱에서는 "AI를 호출하지 못했습니다. 키·모델 이름·네트워크를 확인해 주세요"만 나왔다.
- 앱과 같은 경로(`run_ai` → `ai_match.recommend` → `call_gemini`)로 3번 재현했다. 3번 모두 **Google 쪽 503 과부하**(`This model is currently experiencing high demand`)였고, 키는 정상적으로 읽혔다.
- 모든 예외를 한 문구로 뭉뚱그려서 키 문제처럼 보였던 것이다.
- AI 호출은 원래 메인 프로세스에서 한다. 하위 프로세스에 키를 넘기지 않는 보안 수정(D-7)과는 관계가 없었다.

### 수정
- 503·429 같은 일시적 오류는 1초, 3초 뒤 최대 2번 재시도한다. 재시도도 앱 전체 한도에는 센다.
- 오류 문구를 원인별로 나눴다: 서버 붐빔 / 사용 한도 / 키 / 모델 이름 / 네트워크 / 응답 해석. 끝에는 항상 "지금은 AI 없이 동의어 매칭만 사용 중"을 붙인다.
- 재시도까지 일시적 오류로 끝나면(`AiBusy`) 세션 호출 횟수에서 뺀다.
- "AI 매칭 체험" 버튼을 "샘플 파일로 바로 체험" 바로 옆에 배치했다(가로 컨테이너).
- **테스트가 로컬 `secrets.toml`의 실제 키를 읽고 있던 문제**를 발견했다. "키가 없을 때" 테스트가 키가 있는 상태로 돌고 있었다. conftest에서 빈 secrets로 바꿔 끼우고, 가짜 응답을 끼우지 않은 테스트가 실제 API를 부르면 바로 실패하게 했다.
- 결과: 실제 키로 앱에서 "AI 추천" 5건이 채워졌고, 실행하면 체험 파일에 심은 오류 2건과 일치했다.

  - 실제 키 값을 출력하지 않고 바이트 단위로 대조했고, 전체 기록과 추적 파일 어디에도 없었다.
- **개인정보:**
  - 커밋 작성자 이메일이 개인 메일이었다 → GitHub noreply 주소로 기록 전체를 바꾸기로 했다.
  - 샘플 실사자 이름에 실존 배우 이름(2명)이 있었다 → 가상 이름으로 바꿨다. 정답지 37건은 그대로다.
  - README와 정답지에 "샘플의 회사명·인명은 모두 가상입니다" 문구를 넣었다.
- **Linux 호환성:**
  - Windows 전용 코드는 조건 안에만 있다.
  - 코드 속 경로와 git의 대소문자가 일치한다.
  - 한글 파일명은 NFC다.
  - 이 PC에는 WSL·Docker가 없어서 GitHub Actions(Ubuntu)로 검증한다.

### 클라우드용 제한 (`engine/limits.py`)
- 제한값을 secrets → 환경변수 → 프로필 기본값 순서로 읽는다.
- `EXCEL_MERGER_PROFILE = "cloud"`이면 1GB 서버용 값을 쓴다: 파일 10개, 파일당 5MB, 합계 20MB, 파일당 10,000행, 합계 30,000행, 45초, 동시 작업 1개, 작업별 메모리 400MB.
- 로컬 기본값은 그대로다.
- 설정으로 엔진 안전 상한을 넘길 수 없다. 잘못된 값은 기본값을 쓰고 화면에 "설정 안내"를 표시한다.
- **작업별 메모리 상한:** Linux에서 하위 프로세스에 `RLIMIT_DATA`를 건다.
  - `RLIMIT_AS`는 공유 라이브러리까지 세서 파이썬 시작만으로도 걸릴 수 있어 쓰지 않았다.
  - reader가 `MemoryError`를 "손상된 파일"로 바꾸지 않게 했다.
  - 상한을 넘으면 "메모리가 부족합니다"라고 안내한다. 이 테스트는 Ubuntu에서만 돈다.
- `requirements.txt`에 최소 버전을 고정했다(예: `streamlit>=1.64,<2`). GitHub Actions에서 pytest를 돌리고 README에 배지를 달았다.

### 업로드와 Linux(GitHub Actions)에서 처음 잡힌 문제
- 작성자 이메일을 GitHub noreply 주소로 바꾼 뒤(기록 전체, 파일 내용은 그대로) `master`를 공개 저장소에 올렸다.
- 웹에서 `.streamlit/secrets.toml`과 `.claude/launch.json`은 404(없음)임을 확인했다.
- 첫 CI 실행에서 Windows에서는 보이지 않던 실패가 2건 나왔다.
  - 작업 로그는 로그인해야 보인다. 그래서 실패한 테스트를 공개 주석(annotation)과 요약으로 남기도록 워크플로를 먼저 고쳤다.
- **메모리 상한:** 200MB 상한에서 50MB만 잡아도 `MemoryError`가 났다.
  - openpyxl이 부르는 numpy의 OpenBLAS가 CPU 코어 수만큼 스레드 버퍼를 미리 잡고 있었다.
  - 코어가 많은 클라우드 서버일수록 더 심해지는 문제다.
  - 하위 프로세스의 BLAS·OMP 스레드를 1개로 고정했다. 그 결과 기본 데이터 메모리가 **57MB**가 됐다(CI 진단 주석).
- **깊은 중첩 JSON:** 깊이 5000인 JSON이 Windows에서는 `RecursionError`로 거부됐지만, Linux에서는 C 재귀 한도가 달라 그대로 파싱됐다.
  - 운영체제와 관계없이 같게 동작하도록, 파싱 전에 중첩 깊이(최대 10)를 직접 검사한다.
- 결과: Ubuntu에서 전체 테스트가 통과했다(Linux 전용 메모리 상한 테스트 포함).

## 2026-09-29 — 클라우드 AI 호출 실패 진단

### 증상
Streamlit Cloud에 배포한 앱에서 "AI에게 매칭 추천 받기"를 누르면 "네트워크 연결을 확인해 주세요"가 나오고 세션 횟수가 1회 깎였다. 로컬에서는 정상이었다.

### 확인한 것
- **의존성:** 앱과 엔진이 불러오는 외부 패키지는 streamlit, pandas, openpyxl, pyyaml, google-genai 5개다. 모두 `requirements.txt`에 있어서 빠진 패키지는 없었다.
- **버전 차이:** 새 가상환경에 `requirements.txt`만 설치해 클라우드와 같은 조건을 만들었다.
  - 로컬과 버전이 같았다(google-genai 2.25.0, httpx 0.28.1, pydantic 2.13.5).
  - 이 환경에서도 앱과 같은 경로로 호출이 성공했다. 따라서 **클라우드 환경 쪽 원인**이다.
- **오류 분류:** 오류 분류 코드가 **HTTP 상태 코드가 없는 예외를 모두 "네트워크"로 분류**하고 있었다.
  - 설치 문제(`ImportError`), 키 형식 문제(`UnicodeEncodeError`: Secrets 칸에 붙여 넣다가 따옴표·공백·한글이 섞인 경우), SDK 사용 오류도 전부 "네트워크"로 보였다.
  - 원본 메시지는 어디에도 남지 않아 원인을 알 수 없었다.

### 수정
- 원인별 문구를 나눴다.
  - "AI 기능 구성 요소가 설치되지 않았습니다"
  - "AI 키 형식이 올바르지 않습니다"
  - 실제 연결 오류(ConnectionError, httpx의 ConnectError 등)만 "네트워크"
  - 그 밖은 "예상하지 못한 오류, 관리자가 서버 로그 확인"
- 설치 문제와 키 형식 문제는 Google에 닿지 않았으므로 세션 횟수에서 빼고(`AiSetupError`), 재시도하지 않는다.
- 키 형식은 보내기 전에 검사한다(영문·숫자·`_-.`만).
- 호출이 실패할 때마다 예외 종류와 메시지를 **서버 로그(표준 오류)**에 남긴다(`excel_merger.ai` 로거).
  - 넘겨받은 키 값, `AIza…` 모양, `key=` 파라미터는 `***`로 가린다.
  - 화면에는 여전히 원인별 문구만 보여준다.
- 다음 단계: 다시 배포한 뒤 같은 버튼을 누르고 Streamlit Cloud의 "Manage app → 로그"에서 `[excel-merger AI]` 줄을 보면 실제 원인을 알 수 있다.
